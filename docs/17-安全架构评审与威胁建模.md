# 17 - 安全架构评审与威胁建模

> 本文档用于将安全设计评审从“安全人员经验检查”升级为统一、可追踪的工程流程。参考 Microsoft SDL Threat Modeling、STRIDE 等公开实践，核心思想是从“系统应该如何工作”进一步分析“系统可能如何被滥用”。

## 1. 目标

- 在编码前发现架构级安全问题。
- 对重大设计变化建立安全评审。
- 威胁、控制、Owner 和验证方式可追踪。
- Threat Model 随系统生命周期更新。
- 设计缺陷不依赖上线后扫描才能发现。

## 2. 适用范围

以下 SHOULD 进行安全架构评审：

- 新核心系统。
- 新公网系统。
- 新认证/授权方案。
- 新支付/财务流程。
- 新敏感数据处理。
- 新第三方数据交换。
- 新云/Kubernetes 架构。
- 新 AI Agent。
- 新管理控制台。
- 重大架构重构。

## 3. 安全评审触发

可设置触发器：

- 新系统立项。
- 重大版本。
- 新公网入口。
- 新数据类型。
- 新信任边界。
- 新供应商。
- 重大权限变化。
- 高风险事件复盘要求。

## 4. Security Architecture Review

~~~text
Project Intake
   ↓
Architecture Diagram
   ↓
Data Flow Diagram
   ↓
Threat Modeling
   ↓
Security Requirements
   ↓
Mitigations
   ↓
Security Review
   ↓
Verification
   ↓
Release
~~~

## 5. 输入材料

评审前至少准备：

- 系统架构图。
- DFD。
- 用户/角色。
- 网络边界。
- 数据分类。
- 关键 API。
- 第三方依赖。
- 认证授权方案。
- 部署架构。
- 运维入口。

## 6. Data Flow Diagram

DFD 至少标记：

- Process。
- Data Store。
- External Entity。
- Data Flow。
- Trust Boundary。

目标是明确数据和信任如何流动。

## 7. Trust Boundary

重点边界：

- Internet / Internal。
- User / Admin。
- Office / Production。
- App / Database。
- Tenant / Tenant。
- Company / Third Party。
- Cloud / On-prem。
- AI Model / Tool / Data。

## 8. STRIDE

可作为统一威胁分类方法：

- Spoofing。
- Tampering。
- Repudiation。
- Information Disclosure。
- Denial of Service。
- Elevation of Privilege。

STRIDE 是辅助思考方法，不是唯一方法。

## 9. Abuse Case

除正常 Use Case 外，设计 Abuse Case：

- 普通用户尝试管理员操作。
- 用户访问他人对象。
- 攻击者重复领取优惠。
- 员工大量导出。
- 恶意文件上传。
- 第三方接口返回异常内容。

## 10. Misuse Case

针对业务逻辑分析：

- 状态跳转。
- 金额。
- 审批。
- 退款。
- 权限继承。
- 多租户。
- 批量接口。

## 11. 攻击面

至少识别：

- 公网 API。
- 管理接口。
- Upload。
- Webhook。
- MQ。
- Scheduled Job。
- Admin Console。
- DB。
- Cache。
- Third Party。
- CI/CD。

## 12. 身份模型

Threat Model 必须回答：

- 谁是用户？
- 谁是管理员？
- 服务身份是什么？
- 第三方如何认证？
- Workload 如何认证？
- 权限在哪里执行？

## 13. 授权模型

明确：

- RBAC/ABAC。
- 对象级权限。
- 数据范围。
- 租户。
- 管理员特权。
- Break-glass。

## 14. 数据模型

记录：

- 敏感数据。
- 存储位置。
- 传输。
- 加密。
- 备份。
- 日志副本。
- 第三方共享。

## 15. Secret

分析 Secret：

- 从哪里生成。
- 放在哪里。
- 谁可读。
- 如何轮换。
- 泄露后如何吊销。

## 16. 管理面

所有管理入口应单独评审：

- Admin API。
- Actuator。
- Jenkins。
- Kubernetes。
- Cloud Console。
- Database。
- Debug/JMX。

## 17. Third Party

第三方依赖分析：

- 数据发送什么。
- 第三方被攻破影响什么。
- 超时/故障影响什么。
- Secret 权限。
- 替代/退出方案。

## 18. Supply Chain

架构评审中考虑：

- Dependency。
- CI/CD。
- Builder。
- Artifact。
- Image。
- Deployment Credential。

## 19. Availability Threat

安全架构同时分析：

- DoS。
- 资源耗尽。
- 无限重试。
- 慢查询。
- 单点。
- 第三方故障。
- 队列积压。

## 20. Detection Requirement

每个高风险 Threat 应考虑：

- 能否检测。
- 需要哪些日志。
- 告警条件。
- Runbook。

## 22. Mitigation

优先顺序：

1. 通过设计消除。
2. 降低攻击面。
3. 强化身份授权。
4. 隔离。
5. 检测。
6. 补偿控制。
7. 正式风险接受。

## 23. Security Requirement

Threat Model 结果必须转化为可验证需求，例如：

- 所有 Admin API 只允许管理网。
- 导出接口对象级授权。
- Secret 使用 Vault。
- 第三方调用 3 秒超时。
- 上传文件不可执行。
- 关键操作记录审计。

## 24. Verification

每个重大 Threat 应指定验证方式：

- Code Review。
- SAST。
- SCA。
- Unit/Integration Test。
- DAST。
- Pentest。
- Config Review。
- Chaos Test。

## 25. Security Sign-off

重大项目发布前确认：

- Threat Model 已更新。
- Critical Threat 已处理。
- High Threat 有控制/例外。
- Verification 完成。
- Owner 明确。

Sign-off 不意味着安全团队对业务风险承担最终责任。

## 26. Threat Model 更新

触发更新：

- 新功能。
- 新信任边界。
- 新第三方。
- 新敏感数据。
- 新管理员能力。
- 安全事件。
- 高风险漏洞。

## 27. Architecture Decision Record

重要安全设计决策 SHOULD 使用 ADR 记录：

- 背景。
- 决策。
- 替代方案。
- 风险。
- 后果。
- 日期。
- Owner。

## 28. Security Champion

研发团队可培养 Security Champion：

- 参与 Threat Model。
- 推动安全 Requirement。
- 协助 Code Review。
- 连接安全团队与研发。

Security Champion 不是把安全责任全部转移给开发。

## 29. Review 分级

### Level 1
普通内部系统：Checklist。

### Level 2
公网/敏感系统：Threat Model + Security Review。

### Level 3
核心/高价值系统：正式 Threat Model + 安全测试 + Sign-off。

最终分级由公司确认。

## 30. Common Threat Library

SHOULD 建立公司常见 Threat 模板：

- 越权。
- SQLi。
- SSRF。
- Secret。
- Upload。
- Admin Exposure。
- Third-party。
- Supply Chain。
- Data Export。
- Multi-tenant。

## 31. Reference Architecture

将优秀方案沉淀为：

- 标准认证架构。
- 标准 API Gateway。
- 标准 Secret。
- 标准日志。
- 标准上传。
- 标准管理面。

减少每个团队重新设计。

## 32. 指标

- 新核心项目 Threat Model 覆盖率。
- Threat 按期关闭率。
- 发布前架构 Review 覆盖率。
- Threat Model 导致提前发现问题数量。
- 事件中“已有 Threat Model 但控制失效”比例。

## 33. P0

1. 架构评审触发标准。
2. Threat Model 模板。
3. DFD。
4. STRIDE。
5. 核心项目试点。
6. Security Requirement 跟踪。

## 34. P1

1. Security Champion。
2. Common Threat Library。
3. Reference Architecture。
4. Sign-off。
5. Tool 支持。

## 35. P2

1. Threat Model as Code。
2. Architecture Graph。
3. 自动关联资产/数据/漏洞。
4. 持续 Threat Modeling。

## 36. 审计证据

- DFD。
- Threat Model。
- Security Requirement。
- ADR。
- Review 记录。
- Verification。
- Sign-off。
- 例外。
