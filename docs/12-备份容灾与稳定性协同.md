# 12 - 备份、容灾与稳定性协同

> 本文档用于统一公司安全、备份、容灾、性能和稳定性要求。目标不是把安全和 SRE 分开治理，而是在故障、攻击、误操作和容量压力下仍能维持或恢复关键业务。

## 1. 目标

- 核心业务明确 SLO、RTO、RPO。
- 备份不仅成功，而且可恢复。
- 重大故障具备回退、切换和恢复路径。
- 安全变更不会因为缺少性能评估引入新的可用性风险。
- 容量、超时、重试、熔断、限流和降级有统一原则。
- 故障演练和恢复演练形成闭环。

## 2. 业务分级

建议将系统分为核心、重要、一般，并结合：

- 用户影响
- 业务收入/关键流程
- 数据重要性
- 依赖关系
- 可替代性
- 最大可接受中断时间

不同等级采用不同可用性、备份和容灾要求。

## 3. SLI / SLO

### 3.1 SLI

可观测指标，例如：

- 可用率
- 请求成功率
- P95/P99 延迟
- 错误率
- 吞吐
- 消息积压
- 数据新鲜度

### 3.2 SLO

对 SLI 的目标，例如月度可用率、接口延迟目标、任务按时完成率等。

SLO 应反映用户体验和业务需求，而不是只看主机是否存活。

## 4. Error Budget

成熟阶段可使用 Error Budget 平衡发布速度与稳定性。当可靠性长期低于 SLO 时，应减少高风险变更，优先修复稳定性问题。

## 5. RTO / RPO

- **RTO**：业务中断后允许的最长恢复时间。
- **RPO**：允许丢失的最大数据时间窗口。

核心系统 MUST 明确 RTO/RPO，并通过恢复演练验证，而不是只写在文档中。

## 6. 备份范围

至少评估：

- 数据库
- 对象存储
- 文件
- 配置
- Git/Jenkins 关键配置
- 网络设备配置
- 密钥/证书恢复材料
- Kubernetes 配置/etcd（按架构）
- 关键中间件元数据

## 7. 备份策略

根据数据重要性确定：

- 全量/增量
- 频率
- 保留周期
- 存储位置
- 加密
- 异地副本
- 不可变/离线副本

## 8. 3-2-1 思路

重要数据可参考多副本、多介质和异地/隔离副本的思路。具体实现按公司成本、架构和风险确定。

## 9. 不可变备份

勒索场景下，攻击者常尝试删除备份。核心数据 SHOULD 考虑：

- Object Lock/WORM
- 离线副本
- 独立账号/权限域
- 备份删除双人控制

## 10. 备份权限

备份平台权限应与生产权限适当隔离。普通生产管理员不应默认拥有删除全部备份的能力。

## 11. 备份 Secret

备份配置可能包含密码、Token、证书和连接串。备份文件本身应按敏感数据保护。

## 12. 备份监控

至少监控：

- Job 成功/失败
- 备份大小异常
- 备份耗时异常
- 连续失败
- 存储容量
- 最近成功恢复时间

**MUST：备份失败不能只留在日志中无人处理。**

## 13. 恢复测试

备份成功不等于可以恢复。

恢复测试至少验证：

- 文件是否完整
- 数据库是否可启动
- 应用是否能连接
- 数据一致性是否可接受
- 所需密钥/证书是否可获得
- 恢复耗时是否满足 RTO
- 数据点是否满足 RPO

## 14. 恢复演练频率

核心系统 SHOULD 至少按季度/半年进行恢复抽测或演练；实际周期由业务等级决定。

## 15. 容灾模式

按业务需要选择：

- 单机备份
- 主从
- 集群
- 同城双中心
- 异地灾备
- 多可用区
- 多区域

容灾架构必须验证故障时是否真的能切换。

## 16. 灾备切换

切换前明确：

- 触发条件
- 决策人
- DNS/LB/流量切换方式
- 数据一致性
- Secret/配置
- 回切方案

## 17. 单点故障

核心系统识别：

- 单实例数据库
- 单 Redis
- 单 LB
- 单 DNS
- 单机 Jenkins
- 单出口
- 单证书/密钥依赖
- 单第三方依赖

对不可消除单点准备明确恢复手册。

## 18. 容量管理

定期评估：

- CPU
- Memory
- Disk
- IOPS
- Network
- DB Connection
- Thread
- Queue Lag
- File Descriptor
- Pod/Node 资源

不只看平均值，应关注峰值和增长趋势。

## 19. 容量水位

设置预警和严重阈值，并预留扩容时间。磁盘等不可恢复资源避免只在 99% 时才告警。

## 20. 性能基线

关键接口记录基线：

- QPS/TPS
- P50/P95/P99
- Error Rate
- CPU/Memory
- GC
- DB 慢查询

安全或架构变更上线后对比基线。

## 21. JVM

Java 服务重点：

- Heap
- Old Gen
- GC pause
- Full GC
- Thread count
- Direct Memory
- Metaspace
- CPU
- Safepoint（按需）

JVM 参数必须版本化，避免生产人工修改后无人知晓。

## 22. GC

异常征兆：

- Full GC 频繁
- GC Pause 增大
- Old Gen 持续上升
- 分配速率异常

不要只通过扩大 Heap 掩盖内存泄漏。

## 23. 线程池

每个关键线程池明确：

- core/max
- queue
- rejection policy
- 任务类型
- 监控指标

禁止默认无界队列处理不可控流量。

## 24. 连接池

数据库/HTTP/Redis 连接池关注：

- 最大连接
- 活跃连接
- 等待时间
- 泄漏
- 获取超时

连接池大小应与下游承载能力匹配。

## 25. 超时

所有远程调用必须有超时。超时应形成层级关系，避免上游等待时间比下游更短导致无效工作持续执行。

## 26. 重试

重试必须：

- 有次数上限。
- 指数/抖动退避。
- 区分可重试错误。
- 不盲目重试非幂等写操作。
- 防止多层重试放大。

## 27. 重试风暴

服务故障时大量同步重试可能把局部故障放大为全链路故障。必须结合退避、熔断、限流和降级。

## 28. 熔断

当下游持续失败或超时时及时熔断，保护调用方资源。熔断阈值需基于业务和性能测试调优。

## 29. 限流

限流对象可包括：

- IP
- 用户
- API Key
- 租户
- 接口
- 全局实例

必须考虑突发流量和核心用户。

## 30. 降级

提前定义：

- 哪些功能可关闭
- 哪些数据可返回缓存
- 哪些请求可排队
- 哪些功能必须保证

不要等故障发生才临时决定。

## 31. 隔离

通过线程池、连接池、队列、进程、Pod、租户等隔离高风险工作负载，防止一个功能耗尽全部资源。

## 32. 缓存稳定性

关注：

- 缓存穿透
- 缓存击穿
- 缓存雪崩
- 大 Key
- 热 Key
- TTL 同时过期
- 缓存与数据库一致性

## 33. 数据库稳定性

重点：

- 慢查询
- 锁等待/死锁
- 连接数
- 复制延迟
- 磁盘/IO
- 大事务
- 大表变更
- 索引

## 34. MQ 稳定性

关注消息积压、消费延迟、重复、DLQ、消费者故障、Broker 磁盘和消息大小。

## 35. 第三方依赖

对关键第三方：

- 设置超时。
- 限制并发。
- 熔断。
- 降级。
- 监控 SLA。
- 准备人工/替代流程（如适用）。

## 36. 发布稳定性

生产发布 SHOULD 支持：

- 灰度/滚动
- 健康检查
- 自动/人工回滚
- 发布观察窗口
- 关键指标对比

## 37. 回滚

每次高风险发布明确：

- 回滚版本
- 数据库回滚策略
- 配置回滚
- 回滚触发条件
- 执行人

数据库不可逆变更应单独设计前向修复或兼容迁移。

## 38. Feature Flag

高风险功能 MAY 使用 Feature Flag 控制上线和紧急关闭。Flag 本身需权限和审计。

## 39. 安全变更性能评估

以下安全措施上线前评估性能：

- WAF 新规则
- TLS/加密
- 全量审计日志
- EDR
- 主机扫描
- DAST
- API 限流
- 数据库审计

不能为了安全导致不可接受的生产故障。

## 40. 扫描安全

生产扫描必须控制：

- 并发
- 请求频率
- 时间窗口
- 目标范围
- 停止条件

渗透测试遵循 09 章节授权要求。

## 41. 可观测性

稳定性至少具备：

- Metrics
- Logs
- Traces
- Synthetic/Health Check（按场景）

三者能够通过 Trace ID/服务/资产关联。

## 42. 核心告警

避免仅按基础资源告警，优先覆盖用户影响：

- 可用率下降
- 错误率
- P99 延迟
- 订单/任务失败
- 消息积压
- 数据库连接耗尽
- 依赖超时

## 43. 告警分级

告警应有等级、Owner、Runbook 和升级链。避免大量无动作价值的噪音告警。

## 44. 故障响应

稳定性故障同样应有：

- Incident Commander
- 时间线
- 影响
- 缓解
- 恢复
- 复盘

若包含攻击或安全因素，与 11 安全事件流程合并处理。

## 45. Game Day / 故障演练

可演练：

- 单实例故障
- 数据库主从切换
- Redis 故障
- MQ 积压
- 第三方超时
- DNS/LB 故障
- 证书到期
- 备份恢复
- 某可用区不可用

## 46. Chaos

成熟团队 MAY 引入受控 Chaos Engineering。必须有安全边界、爆炸半径、停止条件和业务知情。

## 47. 复盘

无责复盘重点：

- 触发因素
- 为什么控制没生效
- 为什么影响扩大
- 监控是否及时
- 恢复是否顺畅
- 如何降低再次发生概率

## 48. 变更失败率

SHOULD 跟踪：

- 发布导致回滚比例
- 发布导致事故比例
- 变更后性能恶化

## 49. 指标

- SLO 达标率
- 可用率
- P95/P99
- Error Budget
- 故障 MTTR
- 变更失败率
- 备份成功率
- 恢复测试成功率
- RTO/RPO 达标率
- 容灾演练完成率

## 50. 检查频率

### 每日
- [ ] 核心 SLO/错误率
- [ ] 备份失败
- [ ] 容量严重水位

### 每周
- [ ] 性能趋势
- [ ] 慢查询
- [ ] 消息积压
- [ ] 变更失败/回滚

### 每月
- [ ] 容量预测
- [ ] JVM/连接池基线
- [ ] 备份恢复抽测
- [ ] 第三方 SLA

### 每季度
- [ ] 核心恢复演练
- [ ] RTO/RPO Review
- [ ] 容灾切换/桌面演练
- [ ] SLO Review

## 51. 落地路线

### P0
核心系统 RTO/RPO、备份告警与恢复抽测、基础 SLI/SLO、超时/重试基线、发布回滚。

### P1
不可变备份、容量管理、熔断限流降级、全链路 Trace、标准 Game Day。

### P2
多活/多区域、自动容灾、Chaos、Error Budget 治理、自适应容量和自动回滚。

## 52. 审计证据

RTO/RPO 清单、备份任务、恢复报告、容灾演练、发布记录、回滚记录、SLO 报告、事故复盘和容量报告。
