# 10 - 日志监控与安全运营

> 本文档用于建立公司统一的安全日志、集中监控、告警、检测规则、处置 Runbook 和安全运营度量体系，使安全问题能够被及时发现、分析、升级和闭环。

## 1. 目标

- 关键系统日志可收集、可搜索、时间一致。
- 高风险行为具备检测规则。
- 告警有等级、Owner、SLA 和 Runbook。
- 误报、漏报和规则质量持续优化。
- 安全运营能够与漏洞、资产、应急响应联动。

## 2. 适用范围

优先覆盖防火墙/WAF/VPN、DNS/Proxy、Linux、Windows、AD/IAM、Nginx、Java/Spring、数据库、Redis、Git/Jenkins、云平台、EDR、Kubernetes 和安全扫描平台。

## 3. 日志原则

- **MUST**：关键系统日志能够集中留存。
- **MUST**：关键日志时间同步。
- **MUST**：日志不得无必要记录完整 Secret。
- **SHOULD**：日志具备统一字段和关联 ID。
- **SHOULD**：高风险日志防止普通用户随意删除或篡改。

## 4. 时间同步

服务器、网络设备、数据库、Jenkins、应用、安全设备应使用受控时间源。时区和格式尽量统一，保证跨系统时间线可重建。

## 5. 通用日志字段

适用时至少包含：

- timestamp
- host/device
- source_ip
- destination_ip
- user/account
- action/event
- result
- resource
- request_id / trace_id
- severity
- application
- environment

字段命名应尽量标准化。

## 6. 日志敏感信息

禁止无必要记录：

- 密码
- 完整 Token
- 私钥
- Authorization Header
- 数据库连接 Secret
- 完整个人/客户敏感字段

需要定位问题时使用脱敏值、Hash、ID 或后几位。

## 7. 日志保留

日志保留周期根据业务、调查需求、存储成本、适用法规/合同确认。关键事件日志应足以支撑事件调查和审计。

日志生命周期应包括热存储、归档、删除，并防止无限增长。

## 8. Nginx / Web 日志

至少关注：

- client IP
- method
- URI
- status
- response time
- bytes
- user agent
- upstream
- request/trace ID

避免记录 URL/Query 中的 Secret。必要时对敏感参数脱敏。

## 9. Java / Spring 日志

应用日志 SHOULD：

- 使用结构化日志。
- 带 Trace ID。
- 记录认证/授权失败。
- 记录关键管理员操作。
- 记录关键业务状态变化。
- 不打印完整 Request/Response 敏感数据。
- 异常日志有上下文但不向客户端泄露。

## 10. Linux 日志

重点：

- SSH 登录成功/失败
- sudo
- 用户/组变化
- 服务启动停止
- cron/systemd timer
- auditd（如启用）
- kernel/security
- EDR

## 11. Windows 日志

重点：

- 登录成功/失败
- 用户/组和管理员变化
- 服务创建
- 计划任务
- PowerShell
- RDP
- Defender/EDR
- 安全策略变化

## 12. 数据库日志

根据产品能力记录：

- 登录成功/失败
- 高权限操作
- 用户/权限变化
- DDL
- 大批量数据操作
- 大规模导出
- 审计策略变化

避免因全量 SQL 日志造成严重性能和敏感数据风险，按风险和性能设计。

## 13. VPN 日志

记录用户、源 IP、登录成功/失败、连接时间、断开时间、MFA 状态（平台支持时）和访问策略。

## 14. Firewall / WAF

记录允许/拒绝连接、规则 ID、源/目的、端口、威胁命中、WAF 规则、策略修改。

## 15. Git

重点：

- 登录
- Token 创建/吊销
- 权限变化
- 管理员变化
- 仓库可见性变化
- protected branch 变化
- force push
- 删除仓库

## 16. Jenkins

重点：

- 管理员登录
- 权限变化
- Credentials 变化
- 插件安装/升级
- Job 配置变化
- Pipeline 运行
- Script Console 等高危操作
- Agent 变化

## 17. EDR

EDR 告警至少联动：

- 资产 Owner
- 主机环境
- 进程树
- 用户
- 网络连接
- 文件 Hash
- 隔离状态

严重 EDR 告警应进入安全运营或事件流程。

## 18. 云与 Kubernetes

重点记录：

- 云控制台登录
- IAM/Role 变化
- Security Group 变化
- 对象存储公开权限
- Kubernetes API Audit
- cluster-admin/RBAC 变化
- Secret/Config 访问（按平台能力）

## 19. 日志集中化

关键日志应发送到集中平台，如 SIEM、日志平台或安全数据平台。

要求：

- 来源清单。
- 接入状态监控。
- 解析状态监控。
- 延迟监控。
- 丢日志告警。

## 20. 日志源台账

| 字段 | 说明 |
|---|---|
| Source | 日志源 |
| Asset/Owner | 资产和负责人 |
| Log Type | 类型 |
| Parser | 解析方式 |
| Retention | 保留周期 |
| Criticality | 重要性 |
| Last Seen | 最近收到时间 |

## 21. 告警等级

建议：

| 等级 | 示例 | 处理 |
|---|---|---|
| P1/Critical | 核心资产入侵、高可信凭据泄露 | 立即响应 |
| P2/High | 可疑管理员行为、严重恶意软件 | 快速分析 |
| P3/Medium | 可疑扫描、异常登录 | 当班/工作日处理 |
| P4/Low | 低风险异常 | 汇总与规则优化 |

具体 SLA 由公司确认。

## 22. 核心检测场景

至少建设：

- 暴力破解/密码喷洒
- VPN 异常登录
- 离职账号登录
- 新增管理员
- 高权限变更
- 防火墙/WAF 策略变化
- Web 攻击
- API 越权探测
- 大量 401/403/404/5xx
- 主机异常进程
- 可疑 PowerShell/Shell
- EDR 被关闭
- 横向扫描
- C2/异常外连
- DNS 异常
- 大量数据导出
- Git/Jenkins 高危操作
- 对象存储公开

## 23. 暴力破解

结合账号、源 IP、时间窗口和目标系统聚合，避免仅单次失败产生大量告警。

## 24. 异常登录

结合：

- 新设备
- 新来源 IP
- 异常时间
- 同账号短时间多来源
- 高权限账号
- VPN/IAM 风险信号

不能只以地理位置做唯一判断。

## 25. Web/API 攻击

关联 Nginx、WAF、应用日志。重点识别 SQLi、XSS、路径穿越、SSRF、扫描、敏感接口探测、大量认证失败和异常自动化。

## 26. 横向移动

关注内部主机异常连接 SMB/RDP/SSH/WinRM、凭据使用异常、单主机扫描大网段。

## 27. 数据外泄

关注：

- 大量导出
- 对象存储大量下载
- 非正常时间访问
- 异常外部上传
- DNS/HTTP 异常传输

需要结合业务基线降低误报。

## 28. 告警处置流程

~~~text
告警 → 初筛 → 资产/账号上下文 → 验证
→ 定级 → 处置/升级 → 记录 → 关闭
→ 规则反馈
~~~

## 29. 告警必需上下文

告警尽量带：

- 资产
- Owner
- 环境
- 公网/核心标签
- 用户
- 原始日志
- 规则原因
- 关联事件
- 推荐调查动作

## 30. Runbook

高频高风险规则 SHOULD 有 Runbook，包含：

1. 告警含义。
2. 验证步骤。
3. 所需日志。
4. 误报特征。
5. 遏制动作。
6. 升级条件。
7. 关闭标准。

## 31. 误报管理

误报不是简单关闭告警。记录原因并优化：

- 白名单条件
- 阈值
- 数据源
- 规则逻辑
- 业务基线

白名单需要 Owner 和到期复审，避免永久扩大。

## 32. 漏报管理

安全事件发生但未被检测到时必须反向分析：

- 是否没有日志
- 是否未解析
- 是否规则缺失
- 阈值错误
- 告警被忽略

并形成新检测或日志需求。

## 33. 规则生命周期

~~~text
需求 → 设计 → 测试 → 上线 → 观察 → 调优
→ 定期复审 → 下线/更新
~~~

每条规则应有 Owner、版本、数据源、严重等级、Runbook 和最近复审时间。

## 34. 白名单

白名单必须尽量具体到资产、账号、规则和时间，不采用过宽永久白名单。

## 35. 安全运营与漏洞联动

如果告警涉及已知未修复高危漏洞，应提高处置优先级。新威胁情报出现时，反查公司资产和历史日志。

## 36. 安全运营与事件响应

当告警满足事件条件时，进入 11 章节事件响应流程，不在告警系统中无限分析。

## 37. 值班与升级

明确：

- P1 联系人
- 非工作时间渠道
- 无响应升级人
- 业务/运维联系人
- 紧急隔离权限

## 38. 证据保全

重大事件相关日志不得因正常轮转过早删除。需要时对关键日志、磁盘、内存等按应急流程保全。

## 39. Dashboard

至少展示：

- P1/P2 告警
- 告警趋势
- 日志源健康
- MTTD
- MTTA
- MTTR
- 误报率
- Top 规则
- Top 风险资产

## 40. 指标

- 关键日志接入率
- 日志源在线率
- P1/P2 响应达标率
- MTTD
- MTTA
- 安全事件 MTTR
- 告警误报率
- 规则月度有效命中数
- 漏报复盘数

指标用于发现能力问题，不能只追求告警数量。

## 41. 检查频率

### 每日
- [ ] P1/P2 告警
- [ ] EDR 严重告警
- [ ] 日志源大面积离线
- [ ] 高风险账号行为

### 每周
- [ ] 重复告警
- [ ] 误报 Top 规则
- [ ] 未关闭 P2
- [ ] 新资产日志接入

### 每月
- [ ] 日志覆盖率
- [ ] 规则有效性
- [ ] MTTD/MTTR
- [ ] 白名单到期
- [ ] 漏报和事件复盘

### 每季度
- [ ] 核心检测场景覆盖
- [ ] Runbook 演练
- [ ] 日志保留策略
- [ ] SIEM 权限复审

## 42. 落地路线

### P0
Nginx/Java/Linux/Windows/VPN/Firewall/Git/Jenkins/EDR 核心日志接入，高危告警责任人和 Runbook。

### P1
统一 SIEM、规则治理、资产上下文、Dashboard、值班机制、威胁情报联动。

### P2
UEBA、SOAR、自动隔离/封禁、检测即代码、持续 Purple Team 验证。

## 42.1 ATT&CK 与 Detection Validation

安全运营成熟度不应只用 SIEM 规则数量衡量。

建议使用 MITRE ATT&CK 作为攻击行为的统一语言，并区分：

- Data Source Coverage：是否有足够日志。
- Detection Coverage：是否存在检测规则。
- Validated Coverage：是否通过真实/模拟 TTP 验证。
- Response Coverage：分析员是否能按 Runbook 正确处置。

流程：

~~~text
Threat / TTP
   ↓
Required Telemetry
   ↓
Detection Rule
   ↓
Attack Simulation
   ↓
Alert
   ↓
Analyst Response
   ↓
Gap
   ↓
Improve + Retest
~~~

SHOULD 通过 Purple Team、Atomic Test 或授权攻击模拟持续验证关键检测规则。

Detection Rule 成熟阶段采用 Detection-as-Code：

- Git。
- Review。
- Test。
- Version。
- Deployment。
- Rollback。

详细流程见 19 威胁情报、Red Team 与 Purple Team。

## 43. 审计证据

日志源台账、接入记录、告警工单、Runbook、规则变更、白名单、月报、事件关联记录。
