# 13 - 合规与审计

> 本文档用于把公司安全控制转换为可验证、可追溯的证据和整改闭环。具体适用法律、监管、行业标准、客户合同和认证要求必须由公司法务、合规、业务和安全根据实际情况确认，本章不假定公司当然适用某一特定框架。

## 1. 目标

- 明确公司需要满足哪些外部和内部要求。
- 将要求映射到可执行控制。
- 每个关键控制有 Owner、证据和检查方式。
- 审计发现有风险等级、整改人、截止日期和复测。
- 证据可追溯且不会为了审计临时拼凑。

## 2. 要求来源

可能包括：

- 适用法律法规
- 监管要求
- 行业标准
- 客户合同
- 安全认证
- 公司内部制度
- 管理层风险要求

是否适用必须有明确依据。

## 3. 合规清单

建议维护 Compliance Register：

| 字段 | 说明 |
|---|---|
| Requirement ID | 要求编号 |
| 来源 | 法律/合同/制度等 |
| 适用范围 | 系统/业务/公司 |
| 控制 Owner | 负责人 |
| 控制说明 | 公司如何满足 |
| 证据 | 日志/工单/配置/报告 |
| 检查频率 | 月/季/年 |
| 状态 | 满足/部分/不满足/不适用 |

## 4. 控制库

建立公司统一控制库，避免不同审计重复建设相同控制。

控制可按以下域组织：

- Governance
- Asset
- IAM
- Network
- Endpoint
- Application
- Data
- Supply Chain
- Vulnerability
- Logging
- Incident
- Backup/DR
- Third Party

## 5. 控制字段

每个控制至少包含：

- Control ID
- 名称
- 目的
- MUST/SHOULD
- Owner
- 实施说明
- 证据
- 检查方式
- 检查频率
- 例外方式

## 6. 合规映射

同一个公司控制可以映射多个外部要求。例如资产台账、MFA、漏洞管理、日志和备份通常会被多个框架关注。

原则：

> 先建设真正有效的公司控制，再建立外部标准映射，而不是每来一次审计重新做一套流程。

## 7. 审计类型

可能包括：

- 内部安全检查
- 内部审计
- 客户审计
- 第三方认证审计
- 供应商评估
- 监管检查
- 项目专项检查

## 8. 审计计划

审计前明确：

- 范围
- 控制项
- 时间
- 访谈人员
- 系统/资产
- 抽样方法
- 证据要求
- 输出报告

## 9. 证据原则

证据应：

- 真实
- 有时间
- 有来源
- 有责任人
- 可复核
- 与控制对应
- 保留周期明确
- 防止无关人员修改

## 10. 优先使用系统证据

优先：

- 日志
- 工单
- Git Commit
- CI 构建记录
- IAM 导出
- 扫描报告
- 备份任务
- 监控数据

少依赖纯人工截图。截图可辅助，但不应成为所有控制的唯一证据。

## 11. 证据时间范围

审计证据必须与审计期间匹配。不能用当前配置直接证明过去一年一直如此。

## 12. 证据敏感性

审计材料可能含：

- 用户名单
- IP
- Token
- 配置
- 漏洞
- 客户数据

提供证据时进行最小化和脱敏，并限制审计材料访问。

## 13. 证据库

SHOULD 建立统一证据目录或 GRC 平台，按照：

~~~text
控制 → 系统 → 时间 → 证据
~~~

组织。

## 14. 审计抽样

抽样应具有代表性，不应只挑选“最干净”的系统。

可按：

- 核心/普通
- 生产/测试
- 不同部门
- 不同管理员
- 不同时间段

抽样。

## 15. 审计访谈

访谈用于理解流程，关键控制结论应尽可能由实际证据支持。

## 16. 发现项分类

建议：

- Critical
- High
- Medium
- Low
- Observation/Improvement

风险等级与漏洞等级可以使用一致方法，但审计发现可能涉及流程、治理和证据缺失。

## 18. 整改闭环

~~~text
发现 → 风险确认 → 指派 Owner → 整改计划
→ 实施 → 提交证据 → 复核/复测 → 关闭
~~~

## 19. 根因

对重大/重复审计问题分析根因：

- 制度缺失
- 人员不知道
- 工具能力不足
- 流程不可执行
- 权限设计错误
- 缺乏 Owner
- 资源不足
- 监督机制不足

只修改一条配置而不解决根因，问题通常会重复出现。

## 20. 整改 SLA

整改时间按风险和公司制度确定。重大问题无法按期整改时，进入安全例外或风险接受，而不是简单延期。

## 21. 复测

复测人员应查看实际整改结果和证据，不能只接受“已处理”的文字说明。

## 22. 重复发现

同一问题连续多次审计出现，应提高管理关注级别，并分析为什么整改未持续。

## 23. 例外

控制无法满足时必须：

- 说明差距。
- 评估风险。
- 建立补偿控制。
- 获得有权限人员批准。
- 设置到期时间。

审计人员应能看到例外而不是把例外当成“无问题”。

## 24. 不适用

控制标记 Not Applicable 必须有明确理由和适用边界，不能为了提高通过率随意标记。

## 25. 第三方审计

客户/第三方请求证据时：

- 确认 NDA/授权。
- 最小化提供。
- Secret 脱敏。
- 漏洞细节按 Need-to-Know。
- 记录提供内容。

## 26. 供应商审计

高风险供应商可检查：

- 身份和访问
- 数据保护
- 安全开发
- 漏洞响应
- 事件通知
- 业务连续性
- 分包商管理

## 27. 合同安全条款

重要技术/数据供应商合同 SHOULD 根据业务风险考虑：

- 安全责任
- 数据使用限制
- 访问控制
- 事件通知
- 漏洞修复
- 退出/删除
- 审计权或安全证明

具体条款由法务确认。

## 28. 政策与实际一致

审计重点不只是“有没有制度”，还要验证制度是否真实执行。

例如制度写季度权限复核，则必须存在季度复核记录和整改结果。

## 29. 配置证据

配置类控制最好通过自动化基线扫描、API 导出、配置管理平台获取，降低手工截图成本。

## 30. 持续控制监控

成熟阶段将部分审计从年度抽查变成持续检查，例如：

- MFA 覆盖
- 公网端口
- EDR 覆盖
- Critical 漏洞
- 超期账号
- 备份成功
- 日志接入

## 31. 审计准备

避免临近审计才临时整改。各控制 Owner 应平时维护证据。

## 32. 审计期间变更

审计期间发现问题可以整改，但报告应如实记录发现时间和整改状态，避免把“刚修复”描述为“一直符合”。

## 33. 管理层报告

季度/年度可展示：

- 重大未关闭问题
- 重复发现
- 超期整改
- 控制成熟度
- 风险接受
- 外部审计结果

## 34. 指标

- 审计发现数量
- Critical/High 未关闭数
- 超期整改率
- 重复发现率
- 控制自动取证率
- 证据按时提交率
- 外部审计重大问题数

## 35. 检查频率

### 每月
- [ ] 审计整改超期
- [ ] 重大例外到期

### 每季度
- [ ] 高风险控制抽查
- [ ] 证据库完整性
- [ ] 重复问题

### 每年
- [ ] 适用要求清单复审
- [ ] 制度与控制库复审
- [ ] 年度审计计划

## 36. 落地路线

### P0
适用要求清单、控制 Owner、审计发现台账、整改闭环、证据命名与存放规范。

### P1
统一控制库、外部框架映射、供应商审计、季度控制抽查。

### P2
GRC 平台、持续控制监控、自动证据采集、风险与审计联动。

## 36.1 Security Maturity Scorecard

除“符合/不符合”外，公司可建立能力成熟度 Scorecard。

建议按安全域评估：

- Governance。
- Design。
- Implementation。
- Verification。
- Operations。

可参考 OWASP SAMM 的五大业务功能与安全实践结构，并映射公司 00～24 章节。

成熟度建议使用：

| Level | 特征 |
|---|---|
| L0 | 依赖个人经验 |
| L1 | 有制度和人工流程 |
| L2 | 标准化、自动化、可度量 |
| L3 | 持续验证、平台化、Secure by Default |

Scorecard 用于发现投入优先级与能力差距，不建议直接形成简单部门排名。

### 评估证据

成熟度结论必须有实际证据，例如：

- Pipeline。
- Platform。
- Log。
- Report。
- Exercise。
- Automation。
- Coverage Metric。

不能仅凭“已经制定制度”判断达到高成熟度。

## 37. 审计证据

要求清单、控制库、制度、访谈记录、系统证据、审计报告、发现台账、整改证据、复测、例外和管理层报告。
