# 11 - 安全事件与应急响应

> 本文档用于建立公司安全事件的识别、分级、通报、遏制、取证、清除、恢复和复盘机制。事件响应参考 NIST SP 800-61 Rev.3 的思想：事件响应不是孤立流程，而应嵌入整体网络安全风险管理、检测、响应和恢复活动。

## 1. 目标

- 尽快确认事件真实性和影响范围。
- 控制攻击扩散，优先保护人员、业务和数据。
- 保留足够证据支持调查。
- 安全地恢复业务并持续监控。
- 重大事件形成根因和长期改进。
- 事件过程有角色、时间线和决策记录。

## 2. 适用事件

- 账号入侵
- Web/API 入侵
- 恶意软件/勒索
- 数据泄露或误公开
- Secret/私钥泄露
- 供应链事件
- Git/Jenkins 被入侵
- VPN/IAM 入侵
- DDoS/可用性攻击
- 云账号/资源入侵
- 内部违规或滥用
- 漏洞被真实利用
- 安全设备失效
- 大范围异常数据导出

## 3. 控制原则

- **MUST**：重大事件有明确 Incident Commander。
- **MUST**：关键操作和决策有时间线。
- **MUST**：在清理现场前评估证据保全需要。
- **MUST**：恢复前确认主要攻击路径已得到控制。
- **SHOULD**：重大事件建立独立沟通渠道和固定汇报节奏。

## 4. 事件与告警区别

告警是检测信号；事件是经分析确认需要协调处置的安全问题。并非所有告警都升级为事件，但高可信严重告警必须及时完成判断。

## 5. 事件等级

建议：

| 等级 | 典型影响 | 组织响应 |
|---|---|---|
| SEV1 / Critical | 核心系统入侵、大规模数据泄露、勒索扩散、供应链控制 | 立即跨部门响应与管理层升级 |
| SEV2 / High | 生产主机入侵、高权限账号被控、重要数据泄露 | 紧急响应 |
| SEV3 / Medium | 单点安全问题且影响受控 | 安全/系统团队处置 |
| SEV4 / Low | 低影响事件/可疑行为 | 常规跟踪 |

最终分级根据业务影响、数据、资产、攻击持续性和扩散可能性判断。

## 6. 分级因素

- 是否生产
- 是否核心资产
- 是否公网持续被攻击
- 是否获得管理员权限
- 是否横向移动
- 是否涉及敏感数据
- 是否影响大量用户
- 是否造成业务中断
- 是否供应链影响多个项目
- 攻击者是否仍保持访问

## 7. 应急角色

| 角色 | 职责 |
|---|---|
| Incident Commander | 协调、决策、节奏、升级 |
| Security Lead | 调查、威胁分析、遏制建议 |
| System Owner | 业务影响、系统决策 |
| Ops/SRE | 隔离、变更、恢复、监控 |
| Developer | 应用分析、代码修复 |
| Data Owner | 数据影响判断 |
| Management | 重大业务/风险决策 |
| Legal/Compliance | 适用通知和法律事项 |
| Communications | 对内/对外沟通（适用时） |

小型事件可一人承担多个角色，但责任仍需明确。

## 8. 联系人清单

应维护并定期验证：

- 安全负责人
- SRE/运维值班
- 核心系统 Owner
- 网络负责人
- 数据库负责人
- 管理层升级联系人
- 法务/合规联系人
- 关键供应商联系人

清单应包含非工作时间联系方式。

## 9. 总体流程

~~~text
发现 → 初判 → 分级 → 建立响应团队 → 通报
→ 遏制 → 调查/取证 → 清除 → 恢复
→ 增强监控 → 关闭 → 复盘与整改
~~~

## 10. 发现与初判

初判至少回答：

- 告警/事件是什么？
- 资产是什么？
- 是否真实？
- 是否仍在发生？
- 攻击者可能具有什么权限？
- 是否存在数据风险？
- 是否需要立即隔离？

## 11. SEV1 启动条件

可包括：

- 核心生产系统被入侵
- 大规模勒索/恶意软件
- 统一身份/Git/Jenkins/VPN 被控
- 大量敏感数据泄露
- 攻击者已横向控制多台主机
- 大规模业务中断伴随攻击证据

达到条件后立即指定 Incident Commander。

## 12. 事件时间线

统一使用时间线记录：

| 时间 | 事件/动作 | 执行人 | 结果/证据 |
|---|---|---|---|
| HH:MM | 告警触发 | | |
| HH:MM | 主机隔离 | | |
| HH:MM | 凭据吊销 | | |

时间线是复盘和审计的核心证据。

## 13. 第一时间遏制动作

根据事件类型选择：

- 隔离主机
- 禁用账号
- 吊销 Token
- 轮换 Secret/Key
- 封禁恶意 IP/域名
- WAF 临时规则
- 关闭公网入口
- 停用被利用功能
- 切换备用系统
- 暂停高风险发布

遏制动作必须考虑业务影响和回退。

## 14. 隔离主机

隔离前评估：

- 是否需要保留内存
- 是否会中断核心业务
- 是否有备机
- 是否需要先抓取网络连接/进程信息

必要时通过 EDR 网络隔离而不是立即关机。

## 15. 凭据入侵

如果账号/Token/Key 被控：

1. 禁用或吊销。
2. 强制会话失效。
3. 轮换相关 Secret。
4. 查询历史登录和操作。
5. 检查是否创建后门账号/Token。
6. 检查横向使用。

## 16. Web/API 入侵

重点：

- 保存 WAF/Nginx/应用日志。
- 确认入口 URL。
- 确认利用漏洞。
- 查询 WebShell/恶意文件。
- 查询应用账号权限和数据库访问。
- 修复漏洞或采取临时阻断。
- 检查相同版本其他系统。

## 17. 恶意软件/勒索

- 隔离受影响主机。
- 不随意删除样本。
- 确认传播范围。
- 检查共享目录/域账号。
- 保护备份系统。
- 检查是否存在数据窃取。
- 从可信备份恢复。

## 18. 数据泄露

确认：

- 数据类型
- 数据量
- 暴露起止时间
- 谁可访问
- 是否被下载
- 是否还能访问
- 第三方是否涉及

及时关闭泄露入口并保全访问日志。法务/合规判断是否存在适用通知义务。

## 19. Secret 泄露

Secret 泄露的第一动作是吊销/轮换，而不是只删除 Git 中的文本。然后检查使用日志和传播范围。

## 20. Git/Jenkins 供应链事件

如果 Git/Jenkins 被控，立即评估：

- 管理员账号
- Token/Credentials
- Pipeline 修改
- 构建 Agent
- 制品完整性
- 最近发布版本
- 是否向生产部署恶意制品

必要时暂停发布并验证制品 Hash/来源。

## 21. DDoS/可用性攻击

联合网络/SRE 执行：

- 流量清洗/CDN
- Rate Limit
- WAF/ACL
- 扩容
- 降级非核心功能
- 保护数据库和依赖

同时保留攻击特征用于后续规则。

## 22. 证据保全

重要证据包括：

- 原始日志
- 主机磁盘/文件
- 内存（必要时）
- 进程和网络连接
- 恶意文件 Hash
- 云审计日志
- 账号活动
- 配置变更
- Git Commit/Pipeline

## 23. 证据完整性

重大事件证据 SHOULD 记录采集人、时间、来源、Hash（适用时）和保存位置，限制无关人员访问。

## 24. 取证原则

- 尽量先复制证据再分析。
- 不随意修改原始日志。
- 不让大量人员登录受害主机“看看”。
- 使用受控工具。
- 涉及法律调查时由法务指导更严格流程。

## 25. 根因分析

不仅问“攻击者做了什么”，还要问：

- 为什么能进入？
- 为什么能扩散？
- 为什么没有及时检测？
- 为什么已有控制失效？
- 为什么恢复困难？

## 26. 清除

清除可能包括：

- 删除恶意持久化
- 修复漏洞
- 关闭入口
- 重建主机
- 轮换凭据
- 清理恶意账号
- 更新检测规则

对高风险主机优先考虑从可信镜像重建，而不是只删除一个恶意文件。

## 27. 恢复前检查

- 主要入口已关闭。
- 关键凭据已轮换。
- 恶意持久化已处理。
- 补丁/配置已修复。
- 日志/EDR 正常。
- 数据完整性可接受。
- 回退方案可用。

## 28. 业务恢复

按业务优先级恢复：

1. 核心依赖。
2. 核心业务。
3. 次要业务。
4. 非核心服务。

恢复过程中持续监控，防止攻击者再次进入。

## 29. 事件关闭标准

事件可关闭前应确认：

- 影响范围明确。
- 攻击路径已处理。
- 服务恢复。
- 关键证据保存。
- 短期整改完成。
- 长期整改有 Owner 和时间。

## 30. 复盘

重大事件 SHOULD 在恢复后尽快复盘。

复盘内容：

- 发生了什么
- 时间线
- 影响
- 根因
- 做得好的
- 做得不足的
- 检测缺口
- 流程缺口
- 技术整改
- Owner/Deadline

复盘应以改进为目的，而不是寻找替罪羊。

## 31. 长期整改

可能包括：

- 架构整改
- 权限治理
- 补丁
- 安全编码
- 新检测规则
- 日志补充
- 备份策略
- 培训
- 供应商整改

## 32. 沟通原则

事件信息按 Need-to-Know 分享。不要在公开群传播未脱敏 Token、用户数据、攻击样本和敏感截图。

## 33. 对外沟通

涉及客户、供应商、媒体或监管的外部沟通，应由授权角色统一进行，技术人员不自行对外发布未确认信息。

## 34. 法律/合规升级

是否需要通知客户、监管机构、个人或其他主体，必须由法务/合规依据实际适用法律、合同和事件事实判断。

## 35. 第三方事件

供应商发生事件时：

- 获取事件范围。
- 确认公司数据/账号是否受影响。
- 必要时吊销第三方访问。
- 轮换共享 Secret。
- 加强相关监控。
- 跟踪供应商整改。

## 36. 演练

至少覆盖：

- 账号入侵
- 勒索
- Web 入侵
- 数据泄露
- Git/Jenkins 供应链
- 核心服务不可用

可采用桌面演练、技术演练和联合恢复演练。

## 37. 演练记录

记录场景、参与人、目标、关键决策、问题、整改、下次验证日期。

## 38. 自动化响应

成熟阶段可对高可信场景自动执行：

- EDR 隔离
- 禁用账号
- 封禁恶意 IP
- 吊销 Token
- 创建工单

自动化动作必须防误封，并有回退和审批策略。

## 39. 事件管理工具

事件应有唯一编号和统一记录位置，避免关键时间线散落在多个聊天群。

建议编号：

~~~text
INC-2026-000001
~~~

## 40. 事件记录字段

- 编号
- 标题
- 等级
- 发现时间
- 确认时间
- 发现来源
- 资产
- Owner
- Incident Commander
- 影响
- 时间线
- 遏制动作
- 根因
- 恢复时间
- 整改

## 41. 指标

- MTTD：发现时间
- MTTA：开始响应时间
- MTTC：遏制时间
- MTTR：恢复时间
- SEV1/SEV2 数量
- 重复事件率
- 演练问题关闭率

避免为了指标人为过早关闭事件。

## 42. 检查频率

### 每月
- [ ] 联系人有效
- [ ] 未关闭事件整改
- [ ] SEV1/SEV2 复盘完成

### 每季度
- [ ] 至少一次桌面/专项演练
- [ ] 应急权限验证
- [ ] 证据保存流程检查

### 每年
- [ ] 核心系统综合演练
- [ ] 应急计划复审

## 43. 落地路线

### P0
事件分级、联系人、Incident Commander、时间线模板、核心场景 Runbook、复盘机制。

### P1
事件平台、证据保全规范、跨部门演练、供应商响应、自动升级。

### P2
SOAR、自动遏制、Purple Team 验证、事件与风险/资产平台联动。

## 44. 审计证据

事件工单、时间线、日志、证据清单、决策记录、通报、恢复验证、复盘、整改和演练记录。
