# 公司安全知识图谱

> 当文档数量增长到 00～30 后，不建议按编号从头到尾阅读。本页作为整个 Security Program 的“地图”，用于理解各安全域之间的关系，并根据角色、场景和建设阶段快速找到真正需要看的内容。

> Obsidian 打开方式、Global Graph / Local Graph 和过滤建议见 [[docs/Obsidian使用指南|Obsidian 使用指南]]。

## 1. 怎么使用这张图

建议把文档使用方式从：

~~~text
00 → 01 → 02 → ... → 30
~~~

改成：

~~~text
我现在要解决什么问题？
        ↓
找到对应安全域
        ↓
查看上下游依赖
        ↓
进入 Standard / SOP / Playbook / Template
        ↓
落实 Control ID
        ↓
产生 Evidence
~~~

### 图的核心含义

不是每个安全章节彼此独立，而是一个闭环：

**Governance 决定要求 → Asset 确定保护对象 → IAM/Infrastructure/Application 落实控制 → DevSecOps 把控制工程化 → Vulnerability/Monitoring 验证控制 → Incident/BCP 处理失败 → Audit/Profile 把结果重新反馈给治理层。**

## 8. 文档之间最重要的依赖关系

| 上游 | 下游 | 为什么有关 |
|---|---|---|
| 02 Asset | 09 Vulnerability | 不知道资产，就不知道漏洞覆盖率 |
| 02 Asset | 10 SOC | 不知道资产，就不知道日志有没有漏 |
| 04 IAM | 15 Zero Trust | Zero Trust 的基础是身份 |
| 05 Endpoint | 15 Zero Trust | Device Trust 依赖终端状态 |
| 06 AppSec | 08 DevSecOps | 安全要求需要 CI/CD 自动落实 |
| 17 Threat Model | 06 AppSec | 架构威胁转成应用安全要求 |
| 08 DevSecOps | 09 Vulnerability | SAST/SCA/Secret 最终产生 Finding |

| 10 SOC | 11 IR | 告警最终可能升级为 Incident |

| 07 Data | 26 Privacy | Privacy 建立在数据资产之上 |

| 28 BIA | 12 DR | RTO/RPO 应由业务影响决定 |
| 21 Crypto | 08 DevSecOps | CI/CD、Artifact、Secret 都依赖密钥治理 |
| 30 Awareness | 06/08/10/11 | 人员能力直接影响开发、运营和响应 |

## 10. 维护原则

新增文档时，必须回答三个问题：

1. 它属于知识图谱中的哪个节点？
2. 它和哪些已有节点存在依赖？
3. 它是否真的需要新文档，还是应该补充现有 Standard / SOP / Playbook？

如果无法回答，优先不要新增独立文章。

这样可以避免文档再次从“知识体系”退化成“文章堆积”。
