# 公司安全知识图谱

> 当文档数量增长到 00～30 后，不建议按编号从头到尾阅读。本页作为整个 安全治理体系 的“地图”，用于理解各安全域之间的关系，并根据角色、场景和建设阶段快速找到真正需要看的内容。

> Obsidian 打开方式、全局图谱 / 局部图谱 和过滤建议见 [[docs/Obsidian使用指南|Obsidian 使用指南]]。

## 1. 怎么使用这张图

建议把文档使用方式从：

~~~text
00 → 01 → 02 → ... → 30
~~~

改成：

~~~text
我现在要解决什么问题？
        ↓
找到对应安全域
        ↓
查看上下游依赖
        ↓
进入标准 / SOP / 处置手册 / 模板
        ↓
落实控制 ID
        ↓
产生证据
~~~

### 图的核心含义

不是每个安全章节彼此独立，而是一个闭环：

**治理决定要求 → 资产确定保护对象 → IAM/基础设施/应用落实控制 → DevSecOps 把控制工程化 → 漏洞管理/监控验证控制 → 事件响应/BCP 处理失败 → 审计/安全画像把结果重新反馈给治理层。**

## 7. 控制到证据的知识图谱

~~~mermaid
flowchart LR
    STD["领域标准"] --> CTRL["控制 ID"]
    CTRL --> OWNER["负责人 / 最终责任人"]
    CTRL --> IMPL["实施"]
    IMPL --> EVIDENCE["证据"]
    EVIDENCE --> METRIC["指标"]
    METRIC --> PROFILE["当前安全画像"]
    PROFILE --> GAP["差距"]
    GAP --> ROADMAP["改进路线"]
    ROADMAP --> IMPL

    CTRL --> EX["例外"]
    EX --> RISK["风险接受"]
    RISK --> PROFILE
~~~

这里才是 V2.0 最重要的关系：

> **知识文章只是解释，控制项才是治理单位，证据才能证明控制真正存在。**

| 08 DevSecOps | 09 漏洞管理 | SAST/SCA/凭据扫描最终产生发现项 |
| 09 漏洞管理 | 10 SOC | 重大漏洞需要历史攻击排查 |

## 10. 维护原则

新增文档时，必须回答三个问题：

1. 它属于知识图谱中的哪个节点？
2. 它和哪些已有节点存在依赖？
3. 它是否真的需要新文档，还是应该补充现有 Standard / SOP / Playbook？

如果无法回答，优先不要新增独立文章。

这样可以避免文档再次从“知识体系”退化成“文章堆积”。
